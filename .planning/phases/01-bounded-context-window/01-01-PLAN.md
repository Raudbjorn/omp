# Plan 01-01: Config Cutover and Dual-Mode Guard

<objective>
Replace the 5 assembler budget knobs (hotWindowTurns + 4 percentage-based budget settings) with 2 simpler settings (recentMessageCap + relevanceFloor). Add a fail-closed runtime guard that prevents both legacy compaction and assembler from activating simultaneously.
</objective>

<must_haves>
- 5 old assembler settings removed from schema
- 2 new settings registered: assembler.recentMessageCap (number, default 150000) and assembler.relevanceFloor (number, default 0.0)
- deriveBudget() simplified to use recentMessageCap directly instead of percentage math
- transformContext() in sdk.ts has an explicit guard that throws if both compaction and assembler would run
- Config uses only recentMessageCap + relevanceFloor; legacy knobs removed; startup rejects dual-mode config
</must_haves>

<action>
In `packages/coding-agent/src/config/settings-schema.ts`, in the assembler settings group:

1. **Remove** these 5 settings registrations:
   - `assembler.hotWindowTurns` (number, default 5)
   - `assembler.messageBudgetPercent` (number, default 0.6)
   - `assembler.hydrationBudgetPercent` (number, default 0.15)
   - `assembler.safetyMarginPercent` (number, default 0.1)
   - `assembler.turnBufferPercent` (number, default 0.15)

2. **Add** these 2 settings registrations using the same builder pattern:
   - `assembler.recentMessageCap` — number, default 150000, description: "Hard token cap on recent messages in the active context window. Messages beyond this cap are excluded."
   - `assembler.relevanceFloor` — number, default 0.0, description: "Minimum relevance score (0-1) for older history inclusion. 0.0 includes nothing beyond the cap (Phase 2 placeholder)."

3. **Remove** any associated percentage constants if they exist near the settings:
   - `DEFAULT_SAFETY_MARGIN_PERCENT` (5)
   - `DEFAULT_MESSAGE_BUDGET_PERCENT` (50)
   - `DEFAULT_HYDRATION_BUDGET_PERCENT` (50)

   Note: These constants may be in `message-transform.ts` instead — if so, they are handled by Plan 01-02.
</action>

<task id="2" title="Add dual-mode fail-closed guard in sdk.ts">
<read_first>
- packages/coding-agent/src/sdk.ts (transformContext function at ~line 1440, mode check logic)
- packages/coding-agent/src/context-manager/index.ts (contextManager.mode enum values)
</read_first>
<action>
In `packages/coding-agent/src/sdk.ts`, at the top of `transformContext()` (before any processing begins):

1. Add a dual-mode guard that checks for conflicting configuration:
   ```
   const mode = settings.get("contextManager.mode");
   if (mode === "assembler") {
     // Check if legacy compaction is also enabled
     // The SDK session may have compaction enabled via its own config
     // If both would run, fail closed with a clear error
   }
   ```

2. The guard should:
   - Detect if `contextManager.mode === "assembler"` AND the SDK session's built-in compaction is also active
   - Throw a descriptive error: `"Context management conflict: both assembler and legacy compaction are active. Set contextManager.mode to exactly one of 'compaction' or 'assembler'."`
   - Log the conflict via `logger.error("context-management:dual-mode-conflict", { mode, ... })`

3. The detection mechanism depends on how the SDK exposes compaction state. Read `sdk.ts` to find how compaction is configured. It may be:
   - A setting check: some SDK option that enables auto-compaction
   - A method call: SDK session has a compaction-related property
   - A config overlap: legacy compaction settings still present in config

4. If the SDK doesn't expose compaction state directly, fall back to config-based validation: check that legacy compaction settings are not present when assembler mode is active.
</action>
<acceptance_criteria>
- `sdk.ts` contains `dual-mode-conflict` or `context management conflict` (case-insensitive)
- `sdk.ts` contains a throw/error in the guard path
- `sdk.ts` contains `logger.error` call for the conflict case
- Guard appears BEFORE any `transformMessages` or `ContextBridge` call in `transformContext()`
</acceptance_criteria>
</task>
